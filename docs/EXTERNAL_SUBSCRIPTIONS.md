# Внешние подписки и проверка через Xray

## Как это работает

1. Откройте **Управлять источниками** на главной странице админ-панели.
2. Добавьте название и HTTP(S)-ссылку. При необходимости укажите User-Agent и Authorization в дополнительных настройках.
3. Дождитесь загрузки списка. VPN-проверки планируются автоматически; кнопка **Проверить VPN** ставит ручное задание в ту же очередь.
4. Откройте узлы источника: видны сохранённый статус, задержка, тестовая цель и время завершённой проверки. Кнопка **Обновить результаты** обновляет каталог после фоновой задачи.
5. На странице **Серверы** пользователя выберите источники, количество узлов (1–20), порог задержки и приоритет.
6. Сохраните назначения. Внизу страницы показан итоговый состав и причины недобора.
7. Используйте существующий `/join/:id`. Он объединяет ручные серверы и выбранные узлы источников. Пользователь может иметь только источники.

Выдача строится по БД, без загрузки источников или сетевых тестов во время запроса. Источники с общими конфигурациями не создают дубликаты: в первую очередь учитываются ручные назначения, затем приоритет источников, затем следующие подходящие кандидаты.

Отбор — стабильный top-N, без случайной ротации между пользователями или запросами. Кандидаты ранжируются по доле успехов последнего цикла, приоритету тестовой цели и медианной задержке. Данные подключения внешнего узла, включая UUID, сохраняются. Имена могут меняться.

## Матрица первой версии

| Конфигурация | Автоматический импорт и VPN-проверка |
| --- | --- |
| VLESS TCP / RAW + TLS, `encryption=none` | Да |
| VLESS WebSocket + TLS | Да |
| VLESS TCP / RAW + Reality | Да: `pbk`, `sid`, SNI, fingerprint, `spx`, опциональный `pqv`; `packetEncoding=none` нормализуется в стандартное значение |
| VLESS XHTTP + TLS или Reality | Да: `host`, `path`, `mode`; `extra=null` и поддерживаемые JSON-параметры допускаются |
| VLESS gRPC + TLS или Reality | Да: `serviceName`, `authority`, `mode=gun|multi` |
| VLESS gRPC/Reality с TCP FinalMask fragment (`fm`) | Да: `packets=tlshello`, `delays`, `lengths`, `maxSplit` |
| VLESS TCP / RAW или WebSocket с `security=none` | Да; TLS к VPN endpoint не добавляется |
| SNI, ALPN, поддерживаемый Xray TLS fingerprint | Передаются в TLS-конфиг; у Reality ALPN определяется fingerprint |
| Информационный параметр `Telegram` | Игнорируется и не влияет на fingerprint узла |
| `flow=xtls-rprx-vision` с TCP/TLS или TCP/Reality | Да; с `security=none` этот flow не поддерживается |
| IPv4, IPv6, Unicode-имена, percent-encoding | Да |
| gRPC и другие транспорты, Reality поверх WebSocket | `unsupported`, не попадают в автоматическую выдачу |
| Явный `alpn` в Reality URI | `unsupported`: закреплённое ядро не поддерживает отдельную настройку Reality ALPN |
| `insecure` | Совместимый псевдоним `allowInsecure`; при наличии обоих значения должны совпадать |
| VMess, Trojan, Shadowsocks, Clash YAML, sing-box JSON | Импорт источников в MVP не поддерживает; существующие ручные назначения остаются отдельным механизмом |
| Неизвестные параметры подключения | Не отбрасываются молча; конфигурация считается неподдерживаемой |

Подписки источников: обычный текст, Base64 или Base64URL списка VLESS URI. HTML-ошибка с кодом 200, пустой ответ и неизвестный формат считаются ошибкой источника. Существующий каталог сохраняется. Частично повреждённый ответ обновляет распознанные записи, но не удаляет отсутствующие и сбрасывает HTTP-валидаторы.

Для Reality требуется публичный ключ `pbk`: 32 байта в Base64URL без padding. `sid` — чётное число hex-символов длиной до 16 (может быть пустым), `spx` начинается с `/`. При отсутствии `fp` используется `chrome`, при отсутствии `spx` — `/`. Некорректные ключи и short ID показываются как `invalid`, а не как ошибка запуска Xray.

### Обновление ранее импортированных узлов

После изменения кода остановите приложение через `Ctrl+C` и запустите `npm start`. На старте сохранённые URI повторно разбираются новым парсером. Поддерживаемые конфигурации из прежнего статуса «Не поддерживается» получают состояние «Ожидает VPN-проверки» и попадают в очередь. Повторный разбор также выполняется перед синхронизацией, поэтому ответ `304 Not Modified` этому не мешает.

Назначения источников, присутствие узлов в каталоге и настройки исключения сохраняются. Если несколько написаний URI нормализуются в одну конфигурацию, их история объединяется; исключённый узел автоматически не включается. Изменённая конфигурация получает новое поколение и требует успешного VPN-теста перед выдачей.

## Что подтверждает проверка

Маршрут: **хост приложения → внешний VLESS-сервер → HTTPS-цель**.

- Для цикла запускается отдельный Xray с приватным SOCKS5-входом на `127.0.0.1`, случайной SOCKS-авторизацией и единственным VLESS outbound.
- DNS-адрес VPN endpoint разрешается и проверяется до запуска ядра; Xray получает зафиксированный IP, исходный SNI и WS Host.
- HTTPS-цель передаётся через SOCKS (`socks5h`), без прямого обхода и без наследования внешних proxy-настроек.
- На каждой цели выполняются три новых HTTPS-соединения. Не менее двух HTTP 204 означают `healthy`; задержка — медиана успешных запросов одной цели.
- При неуспехе основной цели проверяется резервная. Их измерения не смешиваются.
- TLS-сертификат HTTPS-цели проверяется во всех режимах, в том числе при `security=none` у внешнего VLESS-узла. HTTP 200, перенаправление и страница авторизации не являются успехом.
- После теста процесс, соединения и временный конфиг удаляются. Локальный SOCKS не публикуется наружу.

Проверка не измеряет скорость скачивания, UDP или задержку от пользовательского устройства. Пользователь подключается непосредственно к выданному внешнему узлу. Постоянный VPN-сервер и TUN на хосте приложения не требуются.

Отдельная TCP-проверка ручных серверов на главной странице показывает только доступность порта.

## Linux и systemd

Требуются Node.js 22+, npm, curl, unzip и sha256sum. Ниже предполагается размещение проекта в `/opt/vpn-subscriptions` и Node в `/usr/bin/node`.

```bash
# В каталоге проекта
npm ci --omit=dev
sudo bash scripts/install-xray.sh
```

Установщик закреплён на **Xray 26.10.21**, проверяет SHA-256 официального архива для x86_64 или arm64 и устанавливает `/usr/local/bin/xray`. GeoIP/GeoSite, публичные inbounds и отдельный systemd-сервис Xray не создаются.

Создайте отдельного системного пользователя для всего приложения и дочерних проверок:

```bash
sudo useradd --system --home-dir /opt/vpn-subscriptions --shell /usr/sbin/nologin vpn-subscriptions
sudo install -d -o vpn-subscriptions -g vpn-subscriptions -m 0700 /opt/vpn-subscriptions/data
cp .env.example .env
# Отредактируйте .env: SESSION_SECRET, ADMIN_PASSWORD, PUBLIC_DOMAIN
sudo chown root:vpn-subscriptions .env
sudo chmod 0640 .env
sudo cp deploy/vpn-subscriptions.service /etc/systemd/system/vpn-subscriptions.service
sudo systemctl daemon-reload
sudo systemctl enable --now vpn-subscriptions
sudo systemctl status vpn-subscriptions
```

При переносе существующей БД предоставьте пользователю `vpn-subscriptions` права на существующий `data/`, включая БД и каталог резервных копий. Исходный код и бинарник Xray должны быть доступны этому пользователю для чтения/запуска. Проверьте путь `command -v node` и при необходимости измените `ExecStart` в unit-файле.

**Node.js и дочерний Xray работают под одним выделенным непривилегированным пользователем.** Переключение UID из непривилегированного Node-процесса не требуется. Unit запрещает повышение привилегий, ограничивает запись каталогом данных и при остановке завершает всю cgroup, включая Xray. Одновременно запускается один владелец `sql.js`.

За HTTPS reverse proxy задайте `HOST=127.0.0.1`, `TRUST_PROXY=1`, `SESSION_COOKIE_SECURE=1`. Публичный адрес QR берётся из `PUBLIC_DOMAIN`. Временные конфиги и БД содержат credentials: каталог данных и его резервные копии доступны только служебному пользователю.

Для обновления ядра сначала проверьте адаптер и интеграционные тесты на новой версии. Затем обновите закреплённый установщик/хеши и `XRAY_VERSION`, перезапустите сервис. Версия ядра и профиль тестирования входят в ключ health: результаты старого профиля не используются для выдачи.

## Windows и PowerShell

Для локальной разработки подходят Windows, Node.js 22+ и PowerShell 5.1+. Установка выполняется из каталога проекта:

```powershell
npm ci
if (-not (Test-Path -LiteralPath ".env")) { Copy-Item ".env.example" ".env" }
.\scripts\install-xray.ps1
```

Установщик выбирает официальный архив **26.10.21** для Windows x64, arm64 или x86, проверяет закреплённый SHA-256 и извлекает `xray.exe` в `tools/xray`. Каталог исключён из Git. Повторная установка с тем же бинарником сохраняет существующий файл. Права администратора для установки в проект не требуются.

Перенесите выведенные значения в `.env`. Например, для текущего каталога проекта:

```dotenv
XRAY_PATH=E:/laragon/www/subscriptions/tools/xray/xray.exe
XRAY_VERSION=26.10.21
PROBE_LOCATION=windows-local
PUBLIC_DOMAIN=
```

В `XRAY_PATH` используйте абсолютный путь; прямые слеши удобны для `.env`. Если значение пустое, приложение автоматически ищет `tools/xray/xray.exe` относительно каталога проекта. `PUBLIC_DOMAIN=` позволяет сформировать локальный QR-код с адресом текущего запроса.

Запустите встроенный VPN-стенд и затем приложение:

```powershell
npm run test:vpn
npm start
```

При `PORT=4000` откройте `http://localhost:4000/admin/subscription-sources`, добавьте реальный источник и дождитесь VPN-проверок. Xray запускается приложением как временный клиент; для завершения приложения используйте `Ctrl+C`, чтобы остановить дочерние проверки и освободить БД.

`test:vpn` читает `.env`, использует установленный Xray и проверяет локальные VLESS TCP/WS с TLS и без TLS, TCP/Reality с Vision и без него, ошибочные UUID/ключи/short ID, TLS/HTTP-ошибки и очистку процессов. Для проверки другого бинарника можно явно задать путь только текущей PowerShell-сессии:

```powershell
$env:XRAY_TEST_PATH = "C:\Tools\Xray\xray.exe"
npm run test:vpn
```

Параметры установщика: `-InstallDir` задаёт каталог установки, `-ArchivePath` позволяет использовать заранее скачанный официальный ZIP с обязательной проверкой той же контрольной суммы.

## Настройки и нагрузка

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `XRAY_PATH` | Linux: `/usr/local/bin/xray`; Windows: `tools/xray/xray.exe` в проекте | Абсолютный путь к ядру; пустое значение выбирает путь для текущей ОС |
| `XRAY_VERSION` | `26.10.21` | Ожидаемая версия; проверяется при запуске |
| `PROBE_LOCATION` | `subscription-host` | Метка региона/хоста измерений |
| `PROBE_HTTP_PROXY` | Пусто | HTTP(S)-прокси `http://user:pass@host:port` для дополнительной проверки: Xray дозванивается до узла через прокси, отдельно сохраняется статус и задержка (бейдж «Прокси») |
| `PROBE_HTTP_PROXY_MODE` | `extra` | `extra` — обычная проверка + дополнительная через прокси (затраты на проверку примерно удваиваются); `only` — все проверки выполняются только через прокси |
| `PROBE_TEMP_DIR` | `data/probes` | Приватные временные конфиги |
| `DB_PATH` | `data/subscription.db` | Файл БД |
| `SOURCE_SYNC_INTERVAL_SECONDS` | `1800` | Начальный интервал импорта; можно изменить у источника |
| `SOURCE_TIMEOUT_SECONDS` | `15` | Общий таймаут загрузки, включая DNS/редиректы |
| `SOURCE_MAX_BYTES` | `5242880` | Лимит сжатого и распакованного ответа |
| `SOURCE_MAX_NODES` | `1000` | Лимит строк снимка; превышение — ошибка, а не усечение |
| `SOURCE_SYNC_CONCURRENCY` | `2` | Параллельные загрузки |
| `PROBE_INTERVAL_SECONDS` | `300` | Целевой интервал между проверками узла после завершения цикла. Срок актуальности результата рассчитывается автоматически: интервал + 15 минут |
| `PROBE_CONCURRENCY` | `4` | Максимум одновременных Xray-процессов |
| `PROBE_MAX_QUEUED` | `2000` | Максимум ожидающих/выполняющихся сетевых задач |
| `PROBE_READY_TIMEOUT_SECONDS` | `5` | Готовность SOCKS-входа |
| `PROBE_ATTEMPT_TIMEOUT_SECONDS` | `5` | Таймаут HTTPS-попытки |
| `PROBE_DEADLINE_SECONDS` | `40` | Общий deadline узла |
| `PROBE_HISTORY_DAYS` | `7` | Максимальный возраст истории |
| `PROBE_HISTORY_MAX_ROWS` | `50000` | Дополнительный предел истории для `sql.js` |
| `PROBE_PRIMARY_URL` | `https://www.gstatic.com/generate_204` | Основная цель, ожидается 204 |
| `PROBE_FALLBACK_URL` | `https://cp.cloudflare.com/generate_204` | Резервная цель, ожидается 204 |
| `PROFILE_UPDATE_INTERVAL_HOURS` | `1` | Одинаковое значение в заголовке и Base64-профиле |

Некорректные интервалы и лимиты останавливают запуск с объяснением. TTL должен превышать интервал проверки, deadline — вмещать запуск ядра и шесть HTTPS-попыток.

Для 300 узлов полный цикл в худшем случае оценивается как `ceil(300 / C) × 40 секунд`: при `C=4` это 50 минут, при `C=12` — около 17 минут. Учитывайте CPU/RAM и фактическую длительность тестов при выборе параллелизма. Интервал 5 минут означает срок постановки узла в очередь, а не гарантию окончания всего каталога за 5 минут.

Очередь непрерывная, объединяет повторные проверки одной конфигурации, чередует источники и повышает приоритет ожидающих задач. Уже работающие узлы назначенных источников получают повышенный приоритет при приближении TTL. Контролируйте длину/возраст очереди и количество свежих рабочих узлов на странице источников.

Статусы `unknown`, `degraded`, `offline`, `test_failed`, `unsupported`, `invalid`, `stale` не заполняют лимит. Последний завершённый неуспешный VPN-тест исключает узел немедленно. Ошибка самого ядра сохраняется отдельно и не продлевает старый успех. Если Xray отсутствует или версия неверна, импорт и выдача продолжают работать; готовность ядра повторно проверяется раз в минуту.

Клиент сам решает, когда обновлять профиль. Отключение узла в сервисе не отзывает уже скачанную VPN-конфигурацию. Если итоговый состав пуст, `/join/:id*` возвращает 404. Квоты источника показываются отдельно и не считаются персональной квотой пользователя.

## Хранение и восстановление

- Миграции версионируются в `schema_migrations`; работают с пустой и существующей БД.
- Импорт, назначения и результаты записываются короткими синхронными транзакциями. Сеть работает вне транзакций.
- Файл сохраняется через временный файл и атомарное переименование; foreign keys включаются также после экспорта `sql.js`.
- При ошибке записи в память восстанавливается последняя сохранённая версия. Планировщик показывает ошибку хранения и прекращает запуск новых задач.
- Создаётся первая резервная копия за день в `data/backups`, хранится до 30 дней. Существующая копия за день не перезаписывается.
- Повреждённая или пустая существующая БД не заменяется автоматически новой. Остановите сервис, сохраните повреждённый файл отдельно и восстановите подходящую копию из `data/backups`.
- После рестарта незавершённые jobs отмечаются прерванными; расписание восстанавливается из БД. systemd завершает старые Xray-процессы, приложение очищает свой временный каталог.
- Удаление источника/пользователя очищает связанные назначения. Смена URL или повторное появление узла требует новой проверки; поздние результаты старого поколения игнорируются.

## Проверки перед развёртыванием

```bash
npm test
npm run test:vpn
```

Обычные тесты не требуют установленного Xray или интернета. Проверяются миграции/транзакции, загрузчик и SSRF, парсеры, жизненный цикл каталога, очередь, TTL, отбор, изоляция пользователей, CSRF и HTTP-выдача.

`test:vpn` поднимает локальные VLESS-серверы, HTTPS-цель и отдельную TLS 1.3/h2-цель для маскировки Reality. Проверяет TCP/WS с TLS и без TLS, TCP/Reality, Vision с TLS/Reality, неверные UUID/`pbk`/`sid`, отсутствие direct fallback, HTTP 200/302, недоверенный TLS-сертификат и очистку процессов/конфигов. Ключи в `test/fixtures` — публичные тестовые данные, не используются при работе сервиса.

После установки добавьте фактический источник и импортируйте `/join/:id` в используемый VPN-клиент. Это отдельная проверка совместимости клиента и реальных транспортов; её нельзя заменить синтетическим стендом. При неподдерживаемой конфигурации страница узла покажет причину, без выдачи непроверенного подключения.
