# План реализации внешних VPN-подписок и отбора работающих серверов

Дата: 16 октября 2026 года.

Зафиксированные ограничения первой версии:

- Основной протокол источников: VLESS.
- Production-сервис работает на Linux.
- Xray-core устанавливается на production-сервере и запускается сервисом от отдельного непривилегированного пользователя только для VPN-проверок.
- Credentials внешних узлов разрешено хранить в БД в открытом виде, но они остаются секретными: не показываются в логах, диагностике и административных списках без явного действия.
- Расчётный размер каталога: около 300 узлов.
- До подтверждения фактических требований источников MVP ограничивается VLESS URI и форматами plain/Base64/Base64URL. Остальные протоколы не входят в критерии первой версии.

## 1. Цель и пользовательский сценарий

Добавить в сервис источники VPN-серверов по HTTP(S)-ссылкам, проверять реальные подключения через эти серверы и включать заданное количество работоспособных узлов в персональные подписки пользователей.

Сценарий администратора:

1. Добавить источник: название и URL внешней подписки.
2. Запустить загрузку списка серверов; далее список обновляется по расписанию.
3. Увидеть результат проверки каждого узла: работоспособность, задержку в миллисекундах, время проверки и причину ошибки.
4. Открыть существующую страницу `/admin/users/:id/servers`.
5. Выбрать отдельные серверы и/или внешние подписки; для каждой подписки задать количество выдаваемых серверов, например 3.
6. Получить по существующей ссылке `/join/:id` объединённый список ручных назначений и отобранных узлов из привязанных источников.
7. При обновлении источника или изменении доступности узлов получать актуальный состав при следующем обновлении подписки в VPN-клиенте.

Термины:

- **Источник** — внешняя ссылка подписки, содержащая список конфигураций.
- **Узел источника** — конкретная конфигурация подключения, включая учётные данные и транспорт.
- **Подписка пользователя** — результат, генерируемый этим сервисом по `/join/:id`.
- **Задержка HTTPS через VPN** — время тестового запроса через проверяемый узел; это показатель, аналогичный URL-test в VPN-клиентах, а не ICMP ping.

## 2. Точки интеграции в текущем проекте

План основан на существующем стеке: Node.js, Express, EJS и SQLite через `sql.js`.

| Место | Текущее поведение | Необходимое расширение |
| --- | --- | --- |
| `src/utils/serverChecker.js` | TCP-соединение с host:port; массовая проверка через неограниченный `Promise.all` | Полноценная VPN-проверка отдельным модулем, ограничение параллелизма, сохранение результатов |
| `src/utils/linkBuilder.js` | Обработка URI и Base64-выдача; подстановка пользовательского UUID для VLESS/Trojan | VLESS-парсер/сериализатор и Base64-выдача; явная политика сохранения исходных credentials |
| `src/db/database.js` | `servers`, `users`, `user_servers`; данные экспортируются целиком при `saveDb()` | Источники, импортированные узлы, привязки источников, результаты проверок и пакетные записи |
| `src/index.js`: `/admin/users/:id/servers` | Назначение отдельных серверов и UUID | Сохранение привязок пользователя к источникам и параметров отбора |
| `src/views/user-servers.ejs` | Чекбоксы серверов и поля UUID | Выбор источников, лимиты выдачи и предпросмотр итогового состава |
| `src/index.js`: `/join/:id`, `/json`, `/qr`, `/qr-img` | Используют только `getUserServersWithUuid()` | Единый сервис разрешения итогового списка, включая пользователей только с внешними источниками |
| `src/views/dashboard.ejs` | Проверка серверов с состояниями «Онлайн/Офлайн» | Ссылка на управление источниками, различение TCP- и VPN-проверки, задержка и время замера |
| `src/index.js`: `startServer()` и shutdown | Есть периодическая задача сброса трафика | Запуск встроенной очереди импорта/проверок и завершение дочерних Xray-процессов |

Ключевые особенности реализации:

- Открытый TCP-порт не подтверждает корректность UUID/пароля, TLS/Reality, транспорта и доступа в интернет.
- Текущая генерация случайного UUID при назначении сервера неприменима к внешним узлам: провайдер ожидает исходные учётные данные.
- Интервал обновления профиля сейчас равен 24 часам и задан одновременно в HTTP-заголовке и внутри Base64-содержимого. Эти значения нужно сделать согласованными и настраиваемыми.
- В текущем `initDb()` часть миграций выполняется до создания базовых таблиц. При добавлении схемы потребуется обеспечить корректный запуск как на существующей, так и на пустой БД.

## 3. Архитектурные решения

### 3.1. Общая схема

```text
URL источника
    -> загрузчик подписки
    -> парсер и нормализация конфигураций
    -> каталог узлов источника
    -> очередь VPN-проверок
    -> сохранённые результаты и задержки

Пользователь + ручные назначения + привязки источников
    -> фильтрация и отбор по сохранённым результатам
    -> устранение дублей
    -> генерация Base64 / JSON / QR
```

Загрузка и сетевые проверки выполняются фоновыми задачами. HTTP-выдача подписки использует локальную БД и актуальность результатов на момент запроса.

Для первой версии использовать один процесс Node.js — владелец `sql.js`, встроенную ограниченную очередь и дочерние процессы **Xray-core** для тестирования. Xray устанавливается на тот же Linux-сервер. Приложение и его дочерние Xray-процессы запускаются под одним выделенным непривилегированным системным пользователем; переключение UID из Node.js не требуется. Результаты сохраняет владелец БД. Второй процесс Node.js с отдельной копией `sql.js` не используется, чтобы исключить взаимную перезапись БД.

### 3.2. Проверяющее ядро

Использовать Xray-core как реальный VPN-клиент: локальный SOCKS5-вход и единственный проверяемый VPN-outbound. HTTPS-запрос выполнять через `https.request` и `socks-proxy-agent` с адресом вида `socks5h://127.0.0.1:<port>`.

- Production-цель: Linux; для локального тестирования поддержать Windows и установку `xray.exe` в каталог проекта.
- Xray устанавливать из проверенного официального релиза; зафиксировать версию, checksum бинарника и способ обновления.
- Запускать Xray только от отдельного непривилегированного пользователя, с закрытым каталогом конфигов и временных файлов, без TUN и изменения системных маршрутов.
- Ограничить доступ к локальному SOCKS-порту только `127.0.0.1`; не открывать его во внешнюю сеть.
- Генерировать собственный минимальный конфиг из нормализованного узла и удалять его после проверки.
- Добавить watchdog, ограничение времени жизни процесса, завершение process group и очистку дочерних процессов при shutdown.
- Матрица поддерживаемых конфигураций: VLESS TCP/TLS и WS/TLS, TCP/Reality с Vision и без него, TCP/WS с `security=none`. gRPC и нестандартные транспорты добавлять после отдельной проверки.
- Учитывать совместимость новой Node.js-зависимости с фактической версией Node.js проекта.

### 3.3. Форматы и учётные данные

Базовый набор входных форматов:

- обычный текст: по одной VLESS-ссылке на строку;
- Base64/Base64URL-кодированный список VLESS-ссылок;
- URI VLESS.

VMess, Trojan, Shadowsocks, Clash YAML и sing-box JSON не входят в MVP. Их добавление возможно отдельными адаптерами после подтверждения реальных источников.

До реализации проверить обезличенные примеры фактических VLESS-подписок. Если источник возвращает Clash YAML или sing-box JSON, это фиксируется как отдельный будущий адаптер и не расширяет MVP автоматически. Неподдерживаемый формат должен давать понятный результат `unsupported_format`, а не пустую успешную загрузку.

Парсер VLESS должен учитывать IPv4/IPv6, percent-encoding, Unicode-названия, UUID, SNI, ALPN, fingerprint, flow, security, тип транспорта, WS host/path и остальные параметры поддерживаемых транспортов. Для Reality поддержать `pbk`, `sid`, `spx`, опциональный `pqv` с проверкой формата ключей и short ID. gRPC service name относится к пока неподдерживаемому транспорту. Неизвестный обязательный параметр нельзя молча отбросить: узел получает `unsupported` или `invalid`.

Для импортированных узлов хранить исходную ссылку и нормализованную конфигурацию. При выдаче использовать исходные credentials; разрешено изменять отображаемое название с учётом формата протокола. Для VMess название находится также в JSON-поле `ps`, поэтому общей операции с `#remark` недостаточно.

Ручные назначения используют существующую персонализацию. При объединении списков у каждого элемента должна быть явная политика `credential_mode: original | user_override`; одного наличия поля UUID для выбора поведения недостаточно. Итоговая конфигурация внешнего узла должна совпадать с проверенной по всем параметрам подключения.

## 4. Модель данных

Импортированные конфигурации хранить отдельно от ручных `servers`: это позволяет выразить принадлежность источнику, автоматический жизненный цикл и исходные credentials без обязательного `user_servers.uuid`.

### `subscription_sources`

- `id`, `name`, `url`, `is_active`, `created_at`, `updated_at`;
- `sync_interval_seconds`, `next_sync_at`;
- `last_attempt_at`, `last_success_at`, `last_error`, `sync_status`;
- `etag`, `last_modified` для условных HTTP-запросов;
- `revision` — версия настроек, защищающая от применения устаревшей загрузки после изменения URL;
- при наличии в ответе — метаданные срока действия и квоты источника, отдельно от пользовательских счётчиков.

### `subscription_nodes`

- `id`, `source_id`, `fingerprint`, `raw_link`, `normalized_config_json`;
- `name`, `protocol`, `host`, `port`;
- `is_present`, `is_enabled`, `capability_status`, `parse_error`;
- `first_seen_at`, `last_seen_at`, `removed_at`;
- уникальность `(source_id, fingerprint)`.

`fingerprint` вычислять как SHA-256 канонической конфигурации подключения, включая credentials, транспорт и параметры безопасности, но исключая отображаемое имя. Одинаковые host:port с разными UUID, паролями или транспортами — разные узлы. Изменение credentials создаёт новую конфигурацию с собственной проверкой.

### `subscription_node_health`

- `node_id` — первичный и внешний ключ;
- `config_fingerprint`, `probe_profile_version`, `probe_location`;
- `status`, `last_attempt_at`, `last_checked_at`, `last_success_at`;
- `latency_ms`, `test_target_id`, `http_status`;
- `successful_attempts`, `total_attempts` для выбранной тестовой цели; `error_code`, очищенное от секретов `error_message`.

`last_checked_at` относится к последнему завершённому VPN-тесту. Ошибка запуска проверяющего ядра не продлевает срок действия прежнего успешного результата.

### `subscription_node_checks`

История измерений: `id`, `job_id`, `node_id`, версия конфигурации/профиля, URL-идентификатор теста, номер попытки, outcome, задержка, HTTP-код, категория ошибки и время. Ограничить срок хранения, например 7 днями. Последнее агрегированное состояние хранится отдельно для быстрой выдачи.

### `user_subscription_sources`

- `user_id`, `source_id` — составной первичный ключ;
- `is_active`, `node_limit` — положительное число, по умолчанию 3;
- `max_latency_ms` — необязательный порог задержки;
- `priority` — порядок обработки нескольких источников;
- `created_at`, `updated_at`.

Привязка означает постоянное правило отбора из источника, а не однократное копирование текущих узлов в `user_servers`.

### `background_jobs`

`id`, тип задачи, `source_id`/`node_id`, состояние, счётчики прогресса, время запуска/завершения и краткая ошибка. Используется для ответа `202 Accepted` и получения результатов фоновой операции. После рестарта незавершённые задачи помечаются прерванными и планируются заново при необходимости.

### Миграции и целостность

- Добавить идемпотентные версионируемые миграции; сначала создавать отсутствующие таблицы, затем выполнять изменения существующих.
- Индексы: узлы по `source_id/is_present`, health по статусу/времени, история по `node_id/checked_at`, привязки по `user_id` и `source_id`, задачи по состоянию.
- Удаление пользователя очищает его привязки; удаление источника — его привязки, узлы и связанные результаты. Согласовать новые связи с текущими обработчиками удаления.
- Выполнять короткие транзакции для применения импорта, сохранения назначений и пакета результатов. Сетевые операции должны завершаться до начала транзакции.
- Сохранять `sql.js` один раз за пакет; обеспечить атомарную замену файла БД через временный файл. Исключить экспорт БД на каждую попытку сетевого теста.

## 5. Загрузка и обновление источников

1. При добавлении или изменении источника проверить URL и сохранить настройки; поставить задачу синхронизации.
2. Загружать ответ с таймаутом, лимитом размера после распаковки и ограничением редиректов. Поддержать необходимые `User-Agent`/заголовки, если это требуется реальными поставщиками.
3. Принимать только HTTP(S). Проверять адреса назначения и редиректы, включая DNS-разрешение, чтобы загрузчик не обращался к loopback, приватной сети или metadata-адресам. Применить аналогичные ограничения к импортированным endpoint-адресам при запуске проверки.
4. Использовать ETag/Last-Modified, сохраняя валидаторы вместе с полностью принятым снимком. Ответ `304` обновляет время успешной синхронизации, но не считается повторной VPN-проверкой. Для частично разобранного ответа новые валидаторы не фиксировать.
5. Определить формат по содержимому, убрать BOM/лишние пробелы, обработать CRLF, декодировать Base64 со строгой проверкой результата. HTML-страница ошибки с HTTP 200 должна распознаваться как ошибка источника.
6. Разобрать ссылки по протоколам, сформировать отчёт: новых, существующих, повторяющихся, неподдерживаемых и некорректных записей.
7. Применить изменения атомарно: добавить новые узлы, обновить имена и `last_seen_at`, сохранить идентичным узлам ID и результаты проверки.
8. Узлы, исчезнувшие из полностью и успешно разобранного снимка, пометить `is_present = 0` и исключить из выдачи. Историю оставить на срок хранения.
9. При частично разобранном ответе разрешить обновление корректных записей, но не удалять отсутствующие по неполному снимку. Пустой или полностью нераспознанный ответ считать ошибкой синхронизации; прошлый каталог сохраняется.
10. Новые, вновь появившиеся и изменившиеся конфигурации отправить на обязательную проверку. При повторном появлении прежняя проверка не заменяет новую.
11. При сетевой ошибке загрузки сохранить последний успешный каталог и показать проблему источника. Дальнейшая выдача старых узлов определяется свежестью их VPN-проверок.
12. Перед применением результата сверить `source.revision`; после изменения URL сбросить HTTP-валидаторы и игнорировать результаты предыдущего URL. Смена URL начинает новый снимок: прежние узлы сохраняются в истории, но исключаются из выдачи до нового импорта и проверки. Отключение источника сразу исключает его из отбора.

URL подписки, включая секреты в пути, query и заголовках, должен быть доступен только административным операциям. В таблицах и логах показывать маскированное значение; публичные ответы содержат отобранные конфигурации, а не ссылку источника.

## 6. Проверка работоспособности через VPN

### 6.1. Последовательность проверки

1. Проверить, что VLESS-конфигурация поддерживается MVP-адаптером и выбранной версией Xray-core.
2. Сгенерировать минимальный конфиг с локальным SOCKS-входом на `127.0.0.1` и единственным outbound проверяемого узла. Предусмотреть безопасное выделение порта и повтор при конфликте.
3. Запустить Xray-core через `spawn` с массивом аргументов, `shell: false`, отдельным непривилегированным пользователем и без наследования внешнего proxy. Дождаться готовности локального входа в пределах отдельного таймаута.
4. Выполнить HTTPS GET на `https://www.gstatic.com/generate_204` через SOCKS5. Резервный URL, например `https://cp.cloudflare.com/generate_204`, задаётся в профиле проверки.
5. Направить весь тестовый запрос через проверяемый outbound; не создавать маршрут `direct` для тестового трафика и не использовать системный proxy fallback. Домен целевого сайта передавать через SOCKS; DNS-разрешение адреса самого VPN-сервера относится к установлению туннеля.
6. Проверить TLS-сертификат HTTPS-цели, ожидаемый HTTP 204 и завершение ответа. Редирект, страница авторизации и произвольный HTTP 200 не считаются успехом. Для другой тестовой цели статус и ожидаемый ответ задаются явно.
7. Выполнить три попытки с новыми HTTPS-соединениями, без HTTP keep-alive и клиентского кэша. Время ожидания очереди и запуска Xray записывать отдельно от сетевой задержки.
8. Успех цикла — минимум 2 из 3 успешных запросов к одной цели. Задержка — медиана успешных измерений этой цели. При провале основной цели проверить резервную с теми же требованиями и общим deadline.
9. Сохранить результаты и агрегированное состояние, если узел всё ещё существует, активен и версия конфигурации актуальна.
10. В `finally` закрыть соединения, остановить дочерний процесс, освободить порт и удалить временный конфиг. Ограничить общий срок жизни процесса даже при зависании запроса.

Таймер на монотонных часах запускается перед установлением SOCKS/HTTPS-соединения и останавливается после получения ожидаемого ответа. Показатель включает установление соединения через VPN и HTTPS-обмен, но исключает запуск проверяющего процесса.

Если основной и резервный URL дают разные результаты, сохранять сведения о каждом. Для отображаемого `latency_ms` всегда указывать использованную цель; измерения разных целей не объединять в одну медиану. При ранжировании учитывать приоритет цели, чтобы не сравнивать задержки разных маршрутов как одинаковые измерения.

### 6.2. Статусы и актуальность

| Статус | Значение | Участие в автоматическом отборе |
| --- | --- | --- |
| `unknown` | Ещё нет завершённой проверки данной конфигурации | Нет |
| `healthy` | Не менее 2 успешных попыток из 3 к одной тестовой цели | Да, пока результат свежий |
| `degraded` | Есть отдельный успех, но порог 2 из 3 не достигнут | Нет; ускоренная повторная проверка |
| `offline` | Проверки через настроенные цели завершились сетевыми ошибками/таймаутами | Нет |
| `test_failed` | Ответ получен, но не соответствует ожидаемому результату | Нет; причина видна отдельно |
| `unsupported` / `invalid` | Ядро/адаптер не поддерживает конфигурацию либо данные некорректны | Нет |
| `stale` | Срок актуальности результата истёк | Нет; вычисляется также при выдаче |

Ошибку самого проверяющего процесса (`runner_error`) хранить отдельно от доступности узла. Она не должна превращать весь пул в `offline`; предыдущее подтверждение действует только до исходного TTL. Аналогично различать DNS, TCP, VPN-handshake, TLS, timeout и unexpected HTTP status там, где причину можно достоверно установить.

TCP-проверку можно оставить как быстрый диагностический режим, явно обозначенный в интерфейсе. Её успех не переводит импортированный узел в `healthy`.

### 6.3. Что подтверждает тест

Проверяется маршрут **хост проверяющего сервиса → VPN-сервер → HTTPS-цель** с конкретной конфигурацией. Задержка с устройства пользователя может отличаться. Успешный GET подтверждает работу этого пути, но не измеряет пропускную способность или поддержку UDP. Поле `probe_location` оставляет возможность позже запускать такие же проверки из нужного региона.

## 7. Фоновые задачи и начальные настройки

| Настройка | Начальное значение |
| --- | --- |
| Обновление внешнего списка | Каждые 30 минут, с переопределением для источника |
| Повторная VPN-проверка активных источников | Каждые 5 минут |
| TTL успешной проверки | 20 минут |
| Таймаут загрузки источника | 15 секунд |
| Максимальный размер ответа источника | 5 MiB после распаковки |
| Лимит узлов на источник | 1000; превышение — ошибка, а не усечение снимка |
| Таймаут готовности ядра | 5 секунд |
| Таймаут одной HTTPS-попытки | 5 секунд |
| Попытки на одну тестовую цель | 3 |
| Общий deadline проверки узла | 40 секунд, включая резервную цель |
| Одновременные VPN-проверки | 4; для 300 узлов полный цикл при deadline 40 секунд может занимать около 50 минут |
| Одновременные загрузки источников | 2 |
| Узлов из одного источника для пользователя | 3; допустимый диапазон 1–20 |
| Предлагаемый интервал обновления профиля клиентом | 1 час |
| Хранение подробной истории проверок | 7 дней |

Все интервалы и лимиты валидируются при запуске. Порог максимальной задержки по умолчанию не ограничен и задаётся в привязке при необходимости.

- Общая очередь объединяет ручные и периодические задания; повторное нажатие возвращает уже запущенное задание для той же конфигурации.
- Приоритет: новые/изменённые узлы, узлы привязанных пользователям источников с истекающим TTL, затем остальной каталог. Предусмотреть справедливый обход, чтобы большой источник не блокировал остальные.
- Для загрузок с повторяющимися ошибками использовать увеличивающуюся задержку повторов; для расписания — небольшой случайный сдвиг времени.
- Обновлять health ограниченными пакетами, сохраняя прогресс долгой задачи. Проверка узла выполняется один раз независимо от числа пользователей, которым привязан источник.
- После рестарта восстановить расписание по сохранённым временным меткам. При shutdown прекратить запуск новых задач и завершить дочерние процессы.
- Контролировать время ожидания очереди, длительность цикла, число свежих `healthy`, ошибки ядра и время последнего успешного импорта.

Настройки стартовые: при `N` узлах, параллелизме `C` и deadline `T` оценка длительности полного цикла в худшем случае — `ceil(N / C) × T`, плюс накладные расходы планировщика. Для 300 узлов, `C = 4` и `T = 40` секунд это около 50 минут; поэтому повторную проверку нельзя планировать как обязательное завершение всего каталога каждые 5 минут. Планировщик должен работать непрерывной приоритетной очередью: сначала новые/изменённые и узлы пользователей, затем узлы с истекающим TTL, с ограничением возраста результата и метрикой отставания очереди. Для фактического объёма подобрать параллелизм/интервалы; просроченные результаты нельзя выдавать как свежие ради заполнения лимита.

## 8. Отбор и генерация подписки пользователя

Добавить единый сервис `resolveUserSubscription(userId, now)`, который возвращает итоговые конфигурации и диагностическое объяснение выбора для админ-панели.

Алгоритм:

1. Получить активного пользователя и его ручные назначения; применить к ним существующие пользовательские overrides.
2. Получить активные привязки к активным источникам, упорядоченные по `priority`, затем ID.
3. Для каждого источника выбрать узлы, которые присутствуют в актуальном каталоге, включены, поддерживаются и имеют `healthy` для текущей конфигурации/профиля проверки.
4. Проверить TTL относительно `now`; применить `max_latency_ms`, если он задан. Последний завершённый неуспешный тест исключает узел даже при более раннем успехе внутри TTL.
5. Ранжировать кандидатов: доля успешных попыток последнего цикла для выбранной цели по убыванию, приоритет тестовой цели, медианная задержка по возрастанию, fingerprint для стабильного порядка.
6. Объединить с ручными назначениями и уже обработанными источниками. Дедупликацию выполнять по итоговой конфигурации после применения credentials, а не по имени или host:port.
7. Добавить до `node_limit` новых уникальных узлов из каждого источника; при дубле брать следующего подходящего кандидата. Лимит относится к источнику, ручные назначения в него не входят.
8. Если подходящих узлов меньше лимита, выдать доступное количество и показать администратору причину недобора. Узлы `unknown`, `offline`, `degraded` и `stale` не используются для заполнения.
9. Сериализовать результат в текущий формат Base64; JSON должен отражать те же узлы и фактические параметры подключения. Учётные данные внешних серверов передавать без подмены.

Список детерминирован при одинаковом состоянии БД и актуальности результатов: повторные запросы не перемешивают серверы случайно. Изменение результатов проверки, каталога или привязок отражается при следующем запросе подписки.

Дополнительные правила:

- Все `/join/:id*` используют общий resolver. Проверку наличия серверов в QR-маршрутах также обновить: пользователь только с внешним источником должен получать рабочий QR своей подписки.
- Если итоговый список пуст, вернуть совместимый с текущим сервисом HTTP 404 с объяснением; не возвращать HTTP 200 с профилем без узлов.
- При отключении пользователя возвращать текущее поведение 404; при отключении источника исключать его вклад сразу.
- Согласованно публиковать настраиваемый `profile-update-interval` в HTTP-заголовке и внутри профиля. Клиенты обновляют список по собственным правилам, поэтому фоновая замена узла в сервисе проявится после обновления подписки клиентом.
- Метаданные трафика внешнего источника показывать как данные источника. Общая upstream-квота и credentials могут использоваться несколькими пользователями; это не персональная квота и не создание нового аккаунта у провайдера.
- Внутренние URL источников, ошибки ядра и диагностические логи в публичную подписку не включать.

## 9. Админ-панель и маршруты

### Управление источниками

Добавить страницу `/admin/subscription-sources` и форму добавления/редактирования:

- название, URL, активность, интервал обновления;
- время последней загрузки, количество узлов и количество свежих работоспособных;
- действия синхронизации и проверки, состояние фоновой задачи;
- просмотр узлов: имя, протокол, host:port, статус, задержка, тестовая цель, время и причина последнего результата;
- включение/исключение отдельного узла из автоматической выдачи;
- отключение и удаление источника с отображением количества привязанных пользователей.

### Назначения пользователя

В `src/views/user-servers.ejs` добавить выбор внешних источников рядом с существующим выбором серверов. Для каждой привязки показывать лимит узлов, необязательный порог задержки и приоритет.

Предпросмотр должен объяснять результат, например: «Запрошено 3, доступно 2», показывать выбранные узлы и время проверки. Сохранение привязки допускается до первой успешной проверки — в таком случае показывается ожидание, а непроверенные узлы в выдачу не попадают.

У внешних источников отсутствует поле пользовательского UUID: credentials берутся из источника. Формы должны поддерживать пользователя, которому назначены только источники и ни одного ручного сервера. Прогресс и ошибки фоновых действий выводить непосредственно на странице.

## 11. Проверки и критерии приёмки

### Автоматические проверки

Добавить тестовый runner, например встроенный `node:test`, и тесты с временной БД и локальными HTTP/SOCKS/VPN-стендами. Проверки основной логики должны быть воспроизводимы без доступа к сторонним подпискам и Google.

1. **Парсеры:** plain/Base64/Base64URL VLESS, IPv6, Unicode, percent-encoding, UUID, TCP/TLS, WS/TLS, TCP/Reality, TCP/WS без TLS; корректные/некорректные ключи Reality, gRPC/неподдерживаемые транспорты, ошибочные строки; round-trip сохраняет credentials и транспорт.
2. **Импорт:** повторная загрузка, ETag/304, редиректы, таймаут, HTTP 200 с HTML, превышение размера/количества узлов, частично некорректный и пустой ответ, удаление/повторное появление узла, смена URL во время задачи.
3. **Реальный путь:** TCP-порт открыт, но VPN-credential неверен; проверка обязана завершиться неуспехом. Отдельно проверить отсутствие обхода через прямое соединение.
4. **Результат HTTP:** ожидаемый 204, неожиданный 200, редирект, неправильный TLS-сертификат, timeout, основная/резервная цель, минимум 2 из 3 и корректная медиана.
5. **Очередь:** соблюдение параллелизма, объединение повторных заданий, общий deadline, освобождение портов/процессов, ошибка отсутствующего ядра и восстановление расписания.
6. **Отбор:** лимит N, меньше N живых, ноль живых, истёкший TTL, последний провал после успеха, максимальная задержка, выключенные источники/узлы, стабильный порядок, дубли и добор из следующих кандидатов.
7. **Изоляция пользователей:** пользователь получает только назначенные источники/серверы; снятие привязки сразу отражается в выдаче.
8. **Credentials и форматы выдачи:** исходные UUID/пароли внешних узлов совпадают с проверенными; ручные overrides корректны; Base64 и JSON содержат один набор; source-only пользователь получает QR.
9. **Безопасность и эксплуатация:** SSRF-защита источников и endpoint-ов, редиректы/DNS rebinding, локальный SOCKS только на loopback, Xray без root, отсутствие proxy fallback, cleanup после timeout и shutdown, отсутствие credentials в логах.
10. **Сохранность:** миграция существующей и пустой БД, повторный запуск, пакетное сохранение результатов, удаление источника/пользователя со связями.

### Сквозная приёмка

- Добавить тестовый источник минимум с пятью конфигурациями: рабочими, недоступной, с неправильными credentials и неподдерживаемой.
- После проверки увидеть сохранённые статусы и задержки рабочих узлов; обновление страницы сохраняет результаты.
- Привязать источник пользователю с лимитом 2 и проверить декодированный `/join/:id`.
- Открыть полученную подписку в используемом VPN-клиенте и подтвердить подключение через каждый выданный узел.
- Сделать один выбранный узел неработоспособным; после следующего завершённого теста и обновления подписки клиентом получить замену из доступного пула либо явный недобор.
- Добавить/удалить узел во внешнем списке, синхронизировать и убедиться в актуализации выдачи без повторного назначения источника пользователю.
- Проверить несколько источников с одинаковыми конфигурациями: дубли отсутствуют, уникальные следующие кандидаты используются для добора.
- Перезапустить сервис: источники, привязки и допустимые по TTL результаты сохраняются, фоновые задачи возобновляются.
- Проверить ожидаемый рабочий объём: очередь укладывается в выбранную политику актуальности, запрос подписки обслуживается из БД независимо от длительности сетевых тестов.

## 13. Уточнения по результатам реализации MVP
